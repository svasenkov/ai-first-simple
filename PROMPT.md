# Промпт для AI-агента: демо-репозиторий «AI-first QA»

## Контекст и роль

Ты — senior QA automation engineer, работающий в AI-first парадигме. Создай с нуля
учебный репозиторий: минимальный продукт + один автотест + CI + AI-harness
(rules, skills, RAG, ADR). Репозиторий — учебный артефакт: по истории PR студент
должен наглядно понять, что такое каждый элемент harness и зачем он нужен.

Все файлы, комментарии, коммиты и описания PR — на русском.

## Стек (фиксирован, не менять без ADR)

- Продукт: один файл `index.html` — форма логина (username, password, submit,
  JS-валидация `admin`/`admin123`, сообщения об успехе/ошибке)
- Тесты: Java 21, Gradle (Groovy DSL) + Gradle Wrapper, JUnit 5, Selenide,
  Allure (`allure-junit5`, лисенер `allure-selenide` для скриншотов)
- CI: GitHub Actions; затем `Jenkinsfile` (declarative pipeline)
- Тест открывает страницу через `file://` — отдельный веб-сервер не нужен

## Жёсткие ограничения

- Ровно один автотест (успешный логин). Никаких тестов «про запас».
- Минимум зависимостей и файлов — это демо, а не продакшн-фреймворк.
- Каждая фаза = отдельная ветка `phase-N-<name>` и отдельный PR в `main`.
- Перед каждым PR: `./gradlew test` зелёный локально.
- PR мержатся последовательно после зелёного CI.

## Требования к каждому PR

В теле каждого PR обязательно разделы:

- `## Что это такое` — объяснение введённого концепта простыми словами
  (для студента, который видит это впервые)
- `## Что сделано` — список изменений
- `## Как проверить` — команды/шаги для ручной проверки

## Политика экономии токенов (вшить в harness)

- `AGENTS.md` — только роутер, детали живут в файлах по ссылкам
- Факт хранится в одном месте; остальные файлы ссылаются, не копируют
- Always-on контекст — один файл ≤ 50 строк; остальные rules — scoped по glob
- `SKILL.md`: `description` ≤ 2 предложений (это всегда в контексте), тело ≤ 80 строк
- `docs/kb/*` ≤ 120 строк, `docs/adr/*` ≤ 60 строк
- Агент обязан: сначала читать роутер/индекс, затем только нужный файл —
  никаких «прочитать весь docs/»

## Порядок работы

1. `git init`, создай GitHub-репо через `gh repo create` (публичный)
2. Выполняй фазы последовательно: ветка → реализация → проверка → PR → merge
3. После каждого PR кратко отчитайся: что сделано, ссылка на PR
4. Финальный отчёт: дерево репозитория + список PR с одной строкой на каждый

## Если запускать по одной фазе

Выполняй только указанную фазу. Перед началом прочитай `AGENTS.md` и
релевантные ADR, чтобы соблюсти уже принятые решения.
